Authentication for MCP servers: the basics of OAuth and API keys

An MCP server checks who is connecting before it returns data. This article covers the kinds of authentication, how specification 2026-07-28 uses OAuth 2.1, the flow of a connection, and what to check before you connect.

I Iqbal Abdullah

An MCP server is a plugin that adds features to an AI application. Once it is connected, the AI can read the data behind the server and carry out actions. So the server needs to know who is connecting and what that party is allowed to do.

This article explains the kinds of authentication an MCP server can use. It then explains how the MCP specification (2026-07-28) uses OAuth. For MCP itself, read Introduction to MCP.

Why a server needs authentication

Take the MCP server of an accounting service. It returns a user's journal entries. If it answered without checking who is asking, it would return other people's data too.

A server checks two things.

  • Authentication: who is connecting
  • Authorization: which data and which actions that party may use

The MCP specification defines this on a page named "Authorization". mcpnavi lists the method of each service in the "Authentication" field.

The kinds of authentication

The "Authentication" field on mcpnavi has four values.

Value Meaning
OAuth 2.1 The user logs in with a browser and grants access, and the client receives an access token. The MCP specification defines this method
API key The provider issues a string (a key). The user sets it in the client, and the client sends it with each request
None The server can be connected to without authentication
Unknown No public page states the method

The authorization page of the MCP specification defines a method based on OAuth 2.1. It does not say how to pass an API key. The way to set an API key differs for each service, so read the provider's documentation.

OAuth 2.1 is a framework that lets an application obtain limited access to a protected resource. The user does not give a password to the client. The client receives an access token with a fixed range of access, called its scope.

How the MCP specification uses OAuth

In the MCP specification, authorization is optional. When an implementation supports it, the rules depend on the transport.

  • HTTP-based transports (such as Streamable HTTP): the implementation should follow the authorization part of the specification.
  • stdio: the implementation does not follow that part, and retrieves credentials from the environment instead. A stdio server runs on the user's own computer.

Over HTTP, there are three roles.

Role What it does
MCP server An OAuth 2.1 "resource server". It accepts requests that carry an access token
MCP client An OAuth 2.1 "client". It sends requests on behalf of the user
Authorization server It interacts with the user and issues access tokens. It may be hosted with the MCP server, or run by a separate entity

The specification asks the following of these three.

Publish where the authorization server is. An MCP server implements OAuth 2.0 Protected Resource Metadata (RFC 9728). This is a document that states where the server's authorization server is. The client reads it to find the authorization server. The server gives the URL of the document in the header of an HTTP 401 response, or serves the document at a well-known URI. This example uses the header:

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         scope="files:read"

Identify the client. Before the authorization flow starts, the client obtains a client ID. There are three ways.

  1. Pre-registration: used when the client and the authorization server already have a relationship.
  2. Client ID Metadata Documents: the client publishes its own details (its name, its redirect URIs and so on) at an HTTPS URL, and uses that URL as its client ID. This is the way for a client and a server with no earlier relationship. The specification recommends that clients and authorization servers support it.
  3. Dynamic Client Registration (RFC 7591): deprecated in specification 2026-07-28. It stays for authorization servers that do not support Client ID Metadata Documents.

Use PKCE. With PKCE, a party that intercepts an authorization code cannot exchange it for a token. An MCP client must implement PKCE. If the authorization server's metadata does not show PKCE support, the client must refuse to proceed.

Bind a token to one server. The client names the MCP server that the token is for, with the resource parameter (RFC 8707). An MCP server accepts only tokens that were issued for it. When an MCP server calls another API, it must not pass on the token it received from the client.

Send the token in a header. The client sends the access token in the Authorization: Bearer <access-token> header. It adds this header to every HTTP request. An access token must not appear in the URL query string.

There are rules for the connection too. Every authorization server endpoint is served over HTTPS. Every redirect URI is either localhost or uses HTTPS.

The flow of an OAuth connection

When a user connects an MCP server for the first time, the client works in this order.

  1. The client sends a request to the MCP server without a token.
  2. The MCP server returns HTTP 401. The WWW-Authenticate header holds the URL of the Protected Resource Metadata.
  3. The client fetches that document and reads where the authorization server is. If the header holds no URL, the client fetches the document from the well-known URI.
  4. The client fetches the authorization server's metadata. It reads the endpoints and confirms PKCE support.
  5. The client opens a browser and shows the authorization server's page.
  6. The user logs in, reads what is shown, and grants access.
  7. The authorization server returns an authorization code to the client.
  8. The client exchanges the authorization code for an access token.
  9. The client sends a request to the MCP server with the access token.

The user acts only in step 6. The client does the rest by itself.

A client may need more access later. In that case the server returns HTTP 403 with the scopes it needs. The client adds those scopes and runs the authorization again. The specification recommends that a client request only the scopes it needs.

How the specification has changed

Each revision has added to or changed the authorization rules.

Revision Main changes to authorization
2025-03-26 Adds an authorization framework based on OAuth 2.1
2025-06-18 Classifies MCP servers as OAuth resource servers and adds Protected Resource Metadata. Requires clients to implement Resource Indicators (RFC 8707)
2025-11-25 Adds OpenID Connect Discovery 1.0 to authorization server discovery. Adds Client ID Metadata Documents as the recommended registration mechanism. Adds incremental scope consent through WWW-Authenticate
2026-07-28 Deprecates Dynamic Client Registration (RFC 7591). Requires a client to compare iss with the recorded issuer when the authorization response includes it. Clarifies that client credentials are bound to the authorization server that issued them

Specification 2026-07-28 also set a policy for deprecated features. A deprecated feature stays in the specification for at least twelve months.

What to check before you connect

Once you know the authentication method, you know what to check before you connect.

  • OAuth 2.1: In the Client ID Metadata Documents flow, the authorization server shows the client's name on the consent page. Read what is shown before you grant access.
  • API key: Read the provider's documentation to find which permissions the key has. Do not put the key in a shared file or a repository.
  • No: The server can be connected to without authentication. The server does not tell one caller from another.

On token storage, the specification requires both clients and servers to store tokens in a protected way. For the details it points to the OAuth 2.1 best practices. It also recommends that authorization servers issue short-lived access tokens.

The authentication method alone is not enough to decide. Check these fields too.

  • Provider: who provides the server (Provider, Type, Japanese entity)
  • Hosting: who runs the server. A server that the provider runs is reached over HTTP, so the OAuth rules above apply. With a stdio server that runs on the user's computer, the credentials are kept in the user's environment.

mcpnavi reads these fields from public pages and lists them with the date they were last checked. A field that no public page states is shown as "Unknown". About the data explains what each field means and how it is checked.

Summary

  • An MCP server's authentication is one of three kinds: OAuth 2.1, API key, or None. When no public page states it, the value is "Unknown".
  • The MCP specification defines authorization based on OAuth 2.1 for HTTP connections. With stdio, credentials come from the environment.
  • An MCP server states where its authorization server is with Protected Resource Metadata. The client uses PKCE and binds each token to one server.
  • Specification 2026-07-28 deprecated Dynamic Client Registration. Client ID Metadata Documents are the recommended way.

To find MCP services, use the list of MCP services. Each service page lists Authentication, Provider and Hosting.
