Remote and local MCP servers: what the difference is

A provider runs a remote MCP server, and you connect to it by URL. You run a local MCP server on your own computer. This article covers hosting versus transport, what the user does, and how credentials are handled.

I Iqbal Abdullah

Descriptions of MCP servers often use the words "remote" and "local". Remote means you connect by URL to a server that the provider runs. Local means you run the server program on your own computer.

This article explains the difference for a reader who is choosing a service. For MCP itself, read the introduction to MCP.

What remote and local mean

An MCP server is a program that works like a plugin: it adds features to an AI application. The official documentation says the term "MCP server" covers this program wherever it runs. It then gives two common names, by where the server runs.

  • Local MCP server: a server that runs on the same machine as the client. The documentation's example is the filesystem server, which works with files. The client launches the server and communicates over stdio.
  • Remote MCP server: a server that runs in the provider's environment. The documentation's example is the Sentry MCP server. It runs on the Sentry platform and communicates over Streamable HTTP.

According to the documentation, a local server that uses stdio typically serves a single client. A remote server that uses Streamable HTTP typically serves many clients.

Hosting and transport are two separate facts

The question "remote or local?" mixes two facts.

  1. Who runs the server: the provider, or the user
  2. How the client and the server communicate: stdio, or Streamable HTTP

mcpnavi lists them separately. The first is "Hosting". The second is "Transport".

Field What it states Values
Hosting Who runs the server Connect by URL, Run it yourself, Unknown
Transport The wire format stdio, Streamable HTTP, SSE (legacy)

They are separate because more than one combination exists.

Hosting Transport What it looks like
Connect by URL Streamable HTTP You give the client the URL of a server that the provider runs
Run it yourself stdio The client launches the program on your own computer
Run it yourself Streamable HTTP You run the program on your own computer or server, and connect to its URL

Because of the third row, "Streamable HTTP" does not mean "the provider runs it". The specification also has text that assumes this case. It is a note about running a Streamable HTTP server locally. It asks the server to bind only to localhost (127.0.0.1).

Some providers offer both forms. For those services, mcpnavi shows both "Connect by URL" and "Run it yourself".

What the user does

When Hosting is "Connect by URL"

The provider runs the server. You register the server's URL in the client. You install no program.

According to the specification, a Streamable HTTP server provides a single HTTP endpoint. It is called the MCP endpoint. It is a URL such as https://example.com/mcp. The client sends each message to this URL as its own HTTP POST.

The content of the exchange passes through the provider's server.

When Hosting is "Run it yourself"

You run the program on your own computer or your own server. With stdio, the steps are:

  1. Follow the provider's instructions and prepare an environment that can run the program.
  2. Register the command that starts the program in the client's settings.
  3. The client launches the server as a subprocess.
  4. The client and the server exchange messages over standard input and standard output.

Steps 3 and 4 are the behaviour the specification defines. The documentation describes stdio this way: processes on the same machine communicate directly, so there is no network overhead.

What stays off the network is the communication between the client and the server. The documentation also lists API calls as an example of what a tool does. A tool on a local server may still call an outside API.

A client that cannot run a program cannot use a service that is "Run it yourself" only. Whether a client can connect depends on Hosting, and also on Transport and Authentication.

How credentials are handled

The handling of the information that identifies the user to the server (an API key or a token) depends on the transport. In the specification, authorization is optional. For implementations that support it, the specification gives a different rule for each transport.

With Streamable HTTP, the recommendation is to follow the specification's authorization flow, which is based on OAuth 2.1. The flow is:

  1. The client opens a browser, and the user approves the connection on the authorization server's page.
  2. The authorization server issues an access token to the client.
  3. The client sends the token in the Authorization header of every request.

The specification says a token must not be placed in the URL query string. According to the documentation, Streamable HTTP also supports standard HTTP authentication methods: bearer tokens, API keys and custom headers. It then recommends OAuth as the way to obtain tokens.

With stdio, the recommendation is not to follow that authorization flow, and to retrieve credentials from the environment instead. There is no approval step in a browser. The server program reads the credentials placed in the environment it runs in.

mcpnavi lists each service's method as "Authentication" (OAuth 2.1, API key, None, Unknown).

The transports in specification 2026-07-28

The current specification, 2026-07-28, defines two standard transports.

  • stdio: The client exchanges messages with a subprocess it launched, over the standard streams. Messages are delimited by newlines.
  • Streamable HTTP: Each message is an HTTP POST to a single MCP endpoint. The reply arrives as one JSON object or as an SSE stream that belongs to that request.

According to the specification, the meaning of the messages is identical on every transport. A transport defines how messages are framed and delivered. Custom transports are also allowed.

Specification 2026-07-28 also changed how Streamable HTTP behaves. The stream opened with GET and the protocol-level sessions were removed.

HTTP+SSE is the transport from specification 2024-11-05. Specification 2025-03-26 replaced it with Streamable HTTP, and it has been "deprecated" since then. The specification says new implementations should not adopt it and existing ones should migrate to Streamable HTTP. It is eligible for removal in a future revision. mcpnavi shows this transport as "SSE (legacy)".

How to read these fields on mcpnavi

mcpnavi lists these facts for each service.

  • Hosting: mcpnavi reads the official documentation and the repository README. A connection URL that the provider runs means "Connect by URL". Instructions for running the program mean "Run it yourself". A connection URL that points at your own computer (localhost) also means "Run it yourself".
  • Transport: every transport the service supports, out of stdio, Streamable HTTP and SSE (legacy).
  • Connection URL: the URL that the provider publishes for connections. It appears under "Setup" on the service's detail page.
  • HTTPS required: a service whose only transport is stdio shows "Not applicable (stdio only)".

A field that no public page states is shown as "Unknown". mcpnavi does not fill in a value by guessing. About the data explains what each field means and how it is checked.

The list of MCP services has a filter named "Connects with a URL alone". It shows only the services whose Hosting includes "Connect by URL".

Summary

  • "Remote" is a server that the provider runs. "Local" is a server that the user runs on their own computer.
  • Who runs the server (Hosting) and how it communicates (Transport) are separate facts. A user can also run a Streamable HTTP server.
  • With "Connect by URL", you register a URL in the client. With "Run it yourself", you prepare the program and register the command that starts it.
  • The handling of credentials depends on the transport. OAuth is recommended with Streamable HTTP. With stdio, credentials come from the environment.
  • Specification 2026-07-28 has two standard transports: stdio and Streamable HTTP. HTTP+SSE is deprecated.
