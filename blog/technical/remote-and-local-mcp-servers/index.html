リモートMCPサーバーとローカルMCPサーバーの違い

リモートMCPサーバーは提供元が動かし、URLで接続します。ローカルMCPサーバーは利用者が手元のPCで動かします。提供形態と接続方式の違い、利用者がすること、認証情報の扱いを説明します。

MCPサーバーの説明には、「リモート」と「ローカル」という言葉がよく出てきます。リモートは、提供元が動かしているサーバーにURLで接続する形です。ローカルは、利用者が手元のPCでサーバーのプログラムを動かす形です。

この記事では、2つの違いを、サービスを選ぶ立場から説明します。MCPそのものの説明は、MCP入門にあります。

リモートとローカルの意味

MCPサーバーは、AIアプリケーションに機能を足すプラグインにあたるプログラムです。公式ドキュメントは、このプログラムがどこで動いていても「MCPサーバー」と呼ぶと説明しています。そのうえで、動く場所によって2つの呼び方を紹介しています。

  • ローカルのMCPサーバー：クライアントと同じPCで動くサーバーです。公式ドキュメントは、ファイルを扱うfilesystemサーバーを例に挙げています。クライアントがこのサーバーを起動し、stdioで通信します。
  • リモートのMCPサーバー：提供元の環境で動くサーバーです。公式ドキュメントは、SentryのMCPサーバーを例に挙げています。Sentryのプラットフォーム上で動き、Streamable HTTPで通信します。

公式ドキュメントによると、stdioを使うローカルのサーバーは、通常1つのクライアントだけを相手にします。Streamable HTTPを使うリモートのサーバーは、通常多数のクライアントを相手にします。

提供形態と接続方式は別の情報

「リモートか、ローカルか」という問いには、2つの情報が混ざっています。

  1. サーバーを誰が動かすか：提供元か、利用者か
  2. クライアントとサーバーがどう通信するか：stdioか、Streamable HTTPか

mcpnaviは、1つ目を「提供形態」、2つ目を「接続方式」として、分けて掲載しています。

項目 表している情報 値
提供形態 サーバーを誰が動かすか URLで接続、自分で動かす、不明
接続方式 通信の形式 stdio、Streamable HTTP、SSE（旧方式）

2つを分ける理由は、組み合わせが1通りではないからです。

提供形態 接続方式 どのような形か
URLで接続 Streamable HTTP 提供元が動かすサーバーに、URLを指定して接続する
自分で動かす stdio クライアントが手元のPCでプログラムを起動する
自分で動かす Streamable HTTP 利用者が自分のPCやサーバーでプログラムを動かし、そのURLに接続する

3つ目の形があるため、「Streamable HTTPなら提供元が動かしている」とは言えません。仕様書にも、この形を前提にした記述があります。Streamable HTTPのサーバーをローカルで動かすときの注意です。待ち受けるアドレスを、localhost（127.0.0.1）だけにするよう求めています。

提供元が2つの形を両方用意しているサービスもあります。mcpnaviは、その場合「URLで接続」と「自分で動かす」の両方を表示します。

利用者がすること

提供形態が「URLで接続」の場合

提供元がサーバーを動かしています。利用者は、サーバーのURLをクライアントに登録します。プログラムのインストールは不要です。

仕様書によると、Streamable HTTPのサーバーはHTTPの窓口を1つ用意します。この窓口を「MCPエンドポイント」と呼びます。https://example.com/mcpのようなURLです。クライアントは、メッセージを1つずつ、このURLにHTTP POSTで送ります。

やり取りの内容は、提供元のサーバーを通ります。

提供形態が「自分で動かす」の場合

利用者が、手元のPCや自分のサーバーでプログラムを動かします。stdioの場合の手順は、次のとおりです。

  1. 提供元の手順に沿って、プログラムを動かせる環境を用意します。
  2. プログラムを起動するコマンドを、クライアントの設定に登録します。
  3. クライアントが、サーバーを子プロセスとして起動します。
  4. クライアントとサーバーが、標準入力と標準出力でメッセージをやり取りします。

手順の3と4は、仕様書が定めている動作です。公式ドキュメントは、stdioを次のように説明しています。同じPCの中のプロセス同士が直接通信するため、ネットワークの負荷がかかりません。

ネットワークを通らないのは、クライアントとサーバーの間の通信です。公式ドキュメントは、ツールの例としてAPI呼び出しも挙げています。ローカルのサーバーでも、ツールが外部のAPIを呼び出す場合があります。

プログラムを動かせないクライアントからは、「自分で動かす」だけのサービスを使えません。クライアントから接続できるかどうかは、提供形態に加えて、接続方式と認証方式にも左右されます。

認証情報の扱い

サーバーが利用者を確認するための情報（APIキーやトークン）の扱いは、接続方式によって変わります。仕様書では、認可の仕組みを実装するかどうかは任意です。実装する場合の方針を、接続方式ごとに分けて書いています。

Streamable HTTPの場合は、OAuth 2.1にもとづく認可の仕様に従うことが推奨されています。流れは次のとおりです。

  1. クライアントがブラウザを開き、利用者が認可サーバーの画面で接続を許可します。
  2. 認可サーバーが、クライアントにアクセストークンを発行します。
  3. クライアントが、リクエストのたびにトークンをAuthorizationヘッダーに入れて送ります。

仕様書は、トークンをURLのクエリ文字列に入れてはならないと定めています。公式ドキュメントによると、Streamable HTTPでは一般的なHTTPの認証も使えます。ベアラートークン、APIキー、独自のヘッダーです。そのうえで、トークンの取得にはOAuthを使うことを推奨しています。

stdioの場合は、この認可の仕様に従わず、認証情報を環境から取得することが推奨されています。ブラウザで許可する流れはありません。サーバーのプログラムは、自分が動いている環境に置かれた認証情報を読み取ります。

mcpnaviは、サービスごとの方式を「認証方式」（OAuth 2.1、APIキー、なし、不明）として掲載しています。

2026-07-28版の接続方式

現在の仕様である2026-07-28版は、標準の接続方式を2つ定めています。

  • stdio：クライアントが起動した子プロセスと、標準入出力でやり取りします。メッセージは改行で区切ります。
  • Streamable HTTP：メッセージごとに、1つのMCPエンドポイントへHTTP POSTを送ります。応答は、1つのJSONか、そのリクエスト専用のSSEストリームで返ります。

仕様書によると、メッセージの意味はどの接続方式でも同じです。接続方式が決めるのは、メッセージの区切り方と届け方です。独自の接続方式を実装することも認められています。

2026-07-28版では、Streamable HTTPの動作も変わりました。GETで開くストリームと、プロトコルのセッションがなくなりました。

HTTP+SSEは、2024-11-05版の接続方式です。2025-03-26版でStreamable HTTPに置き換えられ、それ以来「非推奨」です。仕様書は、新しい実装では採用せず、既存の実装はStreamable HTTPに移行するよう求めています。将来の版で削除される可能性があります。mcpnaviは、この方式を「SSE（旧方式）」と表示します。

mcpnaviでの見方

mcpnaviは、サービスごとに次の情報を掲載しています。

  • 提供形態：公式ドキュメントとリポジトリのREADMEを確認します。提供元が動かしている接続URLの記載があれば「URLで接続」です。自分で動かす手順の記載があれば「自分で動かす」です。接続URLが手元のPC（localhost）を指している場合も「自分で動かす」です。
  • 接続方式：stdio、Streamable HTTP、SSE（旧方式）のうち、対応しているものをすべて表示します。
  • 接続URL：提供元が公開している接続先のURLです。サービスの詳細ページの「導入手順」に表示します。
  • HTTPS必須：接続方式がstdioだけのサービスでは「対象外（stdio のみ）」と表示します。

どの公開ページにも記載がない項目は「不明」と表示します。推測で値を入れることはありません。各項目の意味と確認方法は、掲載されているデータについてで説明しています。

MCPサービス一覧には、「URLだけで接続できる」という絞り込みがあります。提供形態に「URLで接続」を含むサービスだけを表示します。

まとめ

  • 「リモート」は提供元が動かすサーバー、「ローカル」は利用者が手元のPCで動かすサーバーです。
  • サーバーを誰が動かすか（提供形態）と、どう通信するか（接続方式）は、別の情報です。Streamable HTTPのサーバーを利用者が動かす形もあります。
  • 「URLで接続」では、URLをクライアントに登録します。「自分で動かす」では、プログラムを用意し、起動するコマンドをクライアントに登録します。
  • 認証情報の扱いは、接続方式で変わります。Streamable HTTPではOAuthが推奨され、stdioでは環境から取得します。
  • 2026-07-28版の標準の接続方式は、stdioとStreamable HTTPの2つです。HTTP+SSEは非推奨です。
