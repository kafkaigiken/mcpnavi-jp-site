MCPサーバーの認証方式：OAuthとAPIキーの基本

MCPサーバーは、接続してきた相手を確かめてからデータを返します。認証方式の種類、MCP仕様（2026-07-28版）が定めるOAuth 2.1の使い方、接続の流れ、接続前に確認することを説明します。

MCPサーバーは、AIアプリケーションに機能を足すプラグインです。つなぐと、AIはサーバーの先にあるデータを読み、操作を実行できます。そのためサーバーは、接続してきた相手がだれで、何を許されているかを知る必要があります。

この記事では、MCPサーバーの認証方式の種類を説明します。続いて、MCP仕様（2026-07-28版）が定めるOAuthの使い方を説明します。MCPそのものの説明はMCP入門にあります。

認証が必要な理由

会計サービスのMCPサーバーを例にします。このサーバーは、利用者の仕訳データを返します。相手を確かめずに応答すると、ほかの人のデータまで返してしまいます。

サーバーが確かめることは2つあります。

  • 認証：接続してきた相手がだれか
  • 認可：その相手に、どのデータと操作を許すか

MCP仕様は、この仕組みを「Authorization（認可）」というページで定めています。mcpnaviは、サービスごとの方式を「認証方式」の欄に掲載しています。

認証方式の種類

mcpnaviの「認証方式」の欄には、次の4つの値があります。

値 内容
OAuth 2.1 利用者がブラウザでログインしてアクセスを許可し、クライアントがアクセストークンを受け取る方式。MCP仕様が定めている
APIキー 提供元が発行する文字列（キー）をクライアントに設定し、リクエストと一緒に送る方式
なし 認証をせずに接続できる
不明 方式を書いた公開ページが見つからない

MCP仕様の認可のページが定めているのは、OAuth 2.1にもとづく方式です。APIキーの渡し方は書かれていません。APIキーの設定方法はサービスごとに異なるため、提供元のドキュメントで確認します。

OAuth 2.1は、アプリケーションが保護されたリソースへの限定的なアクセスを得るための枠組みです。利用者はパスワードをクライアントに渡しません。クライアントが受け取るのは、範囲（スコープ）の決まったアクセストークンです。

MCP仕様が定めるOAuthの使い方

MCP仕様では、認可の実装は任意です。実装する場合の扱いは、接続方式によって分かれます。

  • HTTPを使う接続方式（Streamable HTTPなど）：仕様の認可の定めに従うことが推奨されています。
  • stdio：仕様の認可の定めには従わず、認証情報を環境から取得します。stdioのサーバーは、利用者のPCで動くサーバーです。

HTTPの場合、登場する役割は3つです。

役割 内容
MCPサーバー OAuth 2.1の「リソースサーバー」。アクセストークンの付いたリクエストを受け付ける
MCPクライアント OAuth 2.1の「クライアント」。利用者の代わりにリクエストを送る
認可サーバー 利用者とやり取りし、アクセストークンを発行する。MCPサーバーと同じ場所にあっても、別の組織が運営していてもよい

仕様は、この3者に次のことを求めています。

認可サーバーの場所を公開する。 MCPサーバーは「OAuth 2.0 Protected Resource Metadata」（RFC 9728）を実装します。これは、自分の認可サーバーがどこにあるかを書いた文書です。クライアントはこの文書を読んで、認可サーバーを見つけます。文書のURLは、HTTP 401の応答のヘッダーか、決まった場所（well-known URI）で知らせます。次は、ヘッダーで知らせる例です。

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         scope="files:read"

クライアントを識別する。 クライアントは、認可の流れを始める前にクライアントIDを用意します。方法は3つあります。

  1. 事前登録：クライアントと認可サーバーに、すでに関係がある場合に使います。
  2. Client ID Metadata Documents：クライアントが自分の情報（名前、リダイレクト先など）をHTTPSのURLで公開し、そのURLをクライアントIDとして使います。事前の関係がない場合の方法で、仕様はこの対応を推奨しています。
  3. 動的クライアント登録（RFC 7591）：2026-07-28版で非推奨になりました。Client ID Metadata Documentsに対応していない認可サーバーのために残されています。

PKCEを使う。 PKCEは、認可コードを横取りされても、トークンに交換できないようにする仕組みです。MCPクライアントにはPKCEの実装が必須です。認可サーバーがPKCEに対応していることをメタデータで確認できない場合、クライアントは処理を中止します。

トークンを1つのサーバー専用にする。 クライアントは、どのMCPサーバーで使うトークンかをresourceパラメーター（RFC 8707）で指定します。MCPサーバーは、自分のために発行されたトークンだけを受け付けます。MCPサーバーが別のAPIを呼ぶ場合も、クライアントから受け取ったトークンをそのまま渡してはいけません。

トークンをヘッダーで送る。 クライアントは、アクセストークンをAuthorization: Bearer <アクセストークン>ヘッダーで送ります。このヘッダーは、すべてのHTTPリクエストに付けます。URLのクエリ文字列にトークンを入れることは禁止されています。

通信にも条件があります。認可サーバーのエンドポイントは、すべてHTTPSで提供します。リダイレクト先のURIは、localhostかHTTPSのどちらかです。

OAuthで接続する流れ

利用者がMCPサーバーを初めてつなぐとき、クライアントは次の順で動きます。

  1. クライアントが、トークンを付けずにMCPサーバーへリクエストを送ります。
  2. MCPサーバーがHTTP 401を返します。WWW-Authenticateヘッダーに、Protected Resource MetadataのURLが入っています。
  3. クライアントがその文書を取得し、認可サーバーの場所を読み取ります。ヘッダーにURLがない場合は、well-known URIから取得します。
  4. クライアントが認可サーバーのメタデータを取得し、エンドポイントとPKCEへの対応を確認します。
  5. クライアントがブラウザを開き、認可サーバーの画面を表示します。
  6. 利用者がログインし、表示された内容を確認して、アクセスを許可します。
  7. 認可サーバーが、認可コードをクライアントに返します。
  8. クライアントが、認可コードをアクセストークンに交換します。
  9. クライアントが、アクセストークンを付けてMCPサーバーへリクエストを送ります。

利用者が操作するのは6だけです。残りはクライアントが自動で行います。

あとから別の権限が必要になることがあります。その場合、サーバーはHTTP 403と、必要なスコープを返します。クライアントは、そのスコープを加えて認可をやり直します。仕様は、クライアントに必要なスコープだけを要求することを推奨しています。

仕様の変遷

認可の定めは、版ごとに追加と変更が続いています。

版 認可に関する主な変更
2025-03-26 OAuth 2.1にもとづく認可の枠組みを追加
2025-06-18 MCPサーバーをOAuthのリソースサーバーと位置づけ、Protected Resource Metadataを追加。クライアントにResource Indicators（RFC 8707）の実装を必須化
2025-11-25 認可サーバーの発見方法にOpenID Connect Discovery 1.0を追加。Client ID Metadata Documentsを推奨の登録方法として追加。WWW-Authenticateによる段階的なスコープの同意を追加
2026-07-28 動的クライアント登録（RFC 7591）を非推奨に変更。認可応答にissがある場合、クライアントが発行者と照合することを必須化。クライアントの資格情報を、発行した認可サーバーにひも付けることを明確化

2026-07-28版は、機能の非推奨についての方針も定めました。非推奨になった機能は、最短でも12か月は仕様に残ります。

接続前に確認すること

認証方式がわかると、接続の前に確かめることが決まります。

  • OAuth 2.1の場合：Client ID Metadata Documentsを使う流れでは、認可サーバーが同意画面にクライアントの名前を表示します。表示された内容を読んでから許可します。
  • APIキーの場合：キーにどの権限があるかを、提供元のドキュメントで確認します。キーを、共有するファイルやリポジトリに含めないでください。
  • なしの場合：認証をせずに接続できます。サーバーは、接続してきた相手を区別しません。

トークンの保管について、仕様はクライアントとサーバーの両方に、保護された形で保管することを求めています。具体的な方法は、OAuth 2.1のベストプラクティスに従うとしています。仕様は認可サーバーに、有効期間の短いアクセストークンを発行することも推奨しています。

認証方式だけでは判断できません。次の欄もあわせて確認します。

  • 提供元：サーバーを提供しているのはだれか（提供元、種別、国内法人）
  • 提供形態：サーバーを動かすのはだれか。提供元が運営するサーバーにはHTTPで接続するため、上のOAuthの定めが関係します。利用者のPCで動かすstdioのサーバーでは、認証情報を利用者の環境に置きます。

mcpnaviは、これらの項目を公開ページから読み取り、情報確認日とともに掲載しています。公開ページに書かれていない項目は「不明」と表示します。項目の意味と確認方法は、掲載されているデータについてで説明しています。

まとめ

  • MCPサーバーの認証方式は、OAuth 2.1、APIキー、なしの3つに分けられます。公開ページからわからないものは「不明」です。
  • MCP仕様が定めているのは、HTTPで接続する場合のOAuth 2.1にもとづく認可です。stdioの場合は、認証情報を環境から取得します。
  • MCPサーバーはProtected Resource Metadataで認可サーバーの場所を知らせます。クライアントはPKCEを使い、トークンを1つのサーバー専用にします。
  • 2026-07-28版で、動的クライアント登録は非推奨になりました。推奨はClient ID Metadata Documentsです。

MCPサービスを探すには、MCPサービス一覧を使います。各サービスのページに、認証方式、提供元、提供形態を掲載しています。

リモートMCPサーバーとローカルMCPサーバーの違い

リモートMCPサーバーは提供元が動かし、URLで接続します。ローカルMCPサーバーは利用者が手元のPCで動かします。提供形態と接続方式の違い、利用者がすること、認証情報の扱いを説明します。
